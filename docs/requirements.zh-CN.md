# DSH Pressure（压力表）· 需求单

> **给 DSH 的 agent 循环装一块压力表：先看见浪费，再决定要不要踩刹车。**

## 0. 一页纸

### 0.1 一句话

**DSH Pressure 不教模型“更努力”，而是把每一轮循环的 token、上下文、工具与时间压力变成可解释的读数，并在浪费变成账单之前，用一个默认关闭、可随时松开的阀门收住。**

### 0.2 要解决的问题

DSH 已经能测量 token、显示统计、在上下文将满时自动压缩，也能在“完全相同的工具调用”重复时提醒模型。但这些能力是分散的、描述性的、事后的：

1. 用户看得到“花了多少”，却很难一眼看出“哪一段、哪一类动作在浪费”。
2. 内置提醒只覆盖精确重复调用；失败重试、上下文抖动、工具结果过胖、预算将尽等浪费信号没有统一的处置层。
3. 官方 agent loop **没有内建 turn 预算**；已有生态里的预算/成本插件各自覆盖一块，但缺少“测量 → 诊断 → 干预 → 回执”的闭环。
4. 很多“效率插件”本身会增加系统提示、工具 schema 或模型调用，形成新的 token 成本。
5. 效率收益缺少可复现的对照方法，最后容易变成“感觉快了”。

### 0.3 方案

四个模块，按用户信任顺序逐层开启：

| 模块 | 作用 | 默认状态 |
|---|---|---|
| **Gauge 仪表** | 每轮/每步的 token、缓存、上下文压力、工具失败、墙钟时间 | 开 |
| **Diagnosis 诊断** | 把原始数字翻译成有证据的浪费信号与建议 | 开（只读） |
| **Valve 阀门** | 预算与阈值；观察、提醒、拦截三档 | 观察 |
| **Receipt 回执** | 每轮一张无正文的效率回执，可导出、可对照 | 开 |

设计上刻意**不注册模型工具**。插件在空闲时几乎不进入模型上下文；只有触发提醒或拦截时，才追加一条短消息或拒绝理由。这样“省 token 的插件”不会先花掉一笔 token。

### 0.4 与现有能力的差异

| 能力 | 已有实现 | 它解决什么 | DSH Pressure 的增量 |
|---|---|---|---|
| 原始统计 | 官方 `sessionStats`、`tokenMeter`、实验性 Statistics 视图 | 精确读数 | 不重做统计；把读数组织成“压力”和“浪费信号” |
| 上下文压缩 | 官方 `compaction-basic`、社区压缩插件 | 把上下文压小 | 不替代压缩；诊断“该不该压、压完是否抖动”，在压缩前后给建议 |
| 重复调用提醒 | 官方 `repeat-tool-reminder` | 精确重复的即时提醒 | 不重复造；只在回执中统计，避免双重提醒 |
| 行为监督 | 社区 `dsh-governor` | 重试风暴、推理预算燃烧 | 学习其“先观察、后强制”的信任路径；本项目补每轮回执、预算阀门与可验证基准 |
| 成本看板 | 社区 `dsh-cost-guard` | 账户/每日成本、自动省钱模式 | 不做账户级账单；聚焦单会话循环内的可回收浪费与工具刹停 |
| 长文阅读 | 社区 `dsh-squeeze` | 用辅助模型读长材料，只回答案 | 不调用辅助模型；本项目不产生额外模型请求 |
| 工具预选 | 社区 `dsh-lean-context` | 减少工具 schema 占用 | 不替换工具发现；本项目假设工具集不变，只处理使用方式 |

> 结论：**不做一个“更大的仪表盘”，做一个“能收住的循环治理层”。** 如果上线后发现某项已有能力已经足够，应删掉重复功能，而不是为了功能表好看而叠加。

### 0.5 成功标准（可测）

| 编号 | 标准 | 验证方式 |
|---|---|---|
| S-01 | 从安装到看到第一张回执 ≤ 3 分钟 | 新机器按 README 实测 |
| S-02 | 观察模式不改变模型输入；额外模型调用 = 0 | 代码审计 + 会话日志对照 |
| S-03 | 空闲 CPU < 1%，常驻内存增量 ≤ 20 MB，单事件折叠 p95 ≤ 2 ms | 基准脚本 |
| S-04 | 回执中的 token 总量与官方 `tokenUsage` 投影误差 ≤ 1% | 同一会话对照 |
| S-05 | 在 9 个循环密集型任务上，强制模式相对基线：工具调用下降 ≥ 20%、token 下降 ≥ 10%，任务成功率不下降 | 预注册基准，报告原始数据 |
| S-06 | 崩溃/重启后不重复生成同一 `(sessionId, turn)` 回执 | 故障注入测试 |
| S-07 | 回执、日志、导出中不含 prompt 正文、工具参数原文、工具结果原文、密钥 | 仓库扫描 + 导出扫描 |
| S-08 | 中文/英文界面、浅色/深色主题、键盘可操作 | 手工验收 + 组件检查 |

### 0.6 明确不做

- 不做压力测试/并发压测工具；本项目里的“压力”指运行时的成本与上下文压力，不是负载测试。
- 不做模型路由、自动换更便宜的模型、自动改写系统提示。
- 不做上下文摘要器；压缩交给官方 `compaction-basic` 或用户已有的压缩插件。
- 不做账户账单、充值、余额查询、团队成本分摊（v1）。
- 不做云端同步、账号体系、遥测。
- 不做“自动替用户决定该不该停”；强制模式必须由用户显式开启，并随时可关。
- 不做“效率分数”这种把多维度压成一个数字的营销指标；v1 只给独立维度和可解释信号。

## 1. 背景与证据

### 1.1 DSH 已经有什么

以下能力在当前运行的 `0.2.2-rc.3` 中已存在；实现前必须复用，而不是重写。

| 能力 | 入口/包 | 对本项目的意义 |
|---|---|---|
| Token/上下文测量 | `ctx.tokenMeter`（`dsh-token-meter`） | `contextPressure(session)` 读最新 prompt 压力；`measure(session)` 在轮末算总量；`tokenUsage` 投影给累计输入/输出/缓存 |
| 会话统计 | `sessionStats`（`dsh-session-stats`） | 整会话 turns/steps、模型时间、工具时间、首 token、解码速度 |
| 自动压缩 | `dsh-compaction-basic` | 压力高时自行压缩；本项目只诊断与建议，不抢它的活 |
| 超大工具结果保留 | `dsh-spill-policy` | 已有 spill 机制；本项目只把“结果过胖”作为信号，不重复裁剪 |
| 精确重复提醒 | `dsh-repeat-tool-reminder` | 已有 3/5/8 次提醒；本项目不重复提醒，只在回执中计数 |
| 原始统计视图 | `dsh-experimental-client-ui-stats` | 已有逐轮/逐步骤表；本项目不做“更全的表”，做“下一步该干什么” |
| Agent 生命周期 | `ctx.agents`、`agent/created`、`agent.ctx` | 绑定每个 agent 的预算与监听，卸载时清理 |
| 工具管线 | `ctx.tools.guard()`、`tools/pre-execute`、`tools/post-execute` | 同步拒绝工具调用；向工具结果追加提醒上下文 |
| 命令 | `ctx.commands.register()` | `/squeeze` 系列命令，不产生模型消息 |
| Web 面板 | Client 插件 + `sidebar.panellist` / `main` slot | 压力面板与入口 |
| 本地 HTTP | `ctx.get('webServer').register()` | 面板只读取数；不新开端口 |
| 打包分发 | `dsh.bundle.patch` + `cordis.patch.yml` | `dsh plugin add` / Plugin Manager 安装 |

### 1.2 真实缺口

| 编号 | 缺口 | 证据/现状 | 影响 |
|---|---|---|---|
| G-01 | 读数分散 | token 在输入框附近、统计在实验视图、压缩在设置里、工具失败在轨迹里 | 用户要拼图，无法在“这一轮”层面做判断 |
| G-02 | 描述多、诊断少 | 官方统计给的是 turns/tokens/time，不判断“哪类动作可回收” | 用户知道贵，不知道贵在哪、下一步改什么 |
| G-03 | 干预碎片化 | 重复提醒只覆盖精确重复；失败重试、上下文抖动没有统一处置 | 同一种浪费在不同插件里各管一段，容易漏 |
| G-04 | 没有 turn 预算 | `dsh-agent-loop` README 明确写“No built-in turn budget” | 长任务可能一直加工具调用，直到用户手动停 |
| G-05 | 没有可信回执 | 多数插件展示实时数字，不产出可对照、可导出的轮末回执 | 无法回答“这插件到底有没有用” |
| G-06 | 插件自身有成本 | 注册工具、加系统提示、每步调用模型都会增加 token | “省 token”可能先花 token |
| G-07 | 隐私风险 | 会话日志含正文；诊断如果复制正文，会制造第二份敏感数据 | 用户不敢开、不敢导出 |

### 1.3 从已有落地项目学到什么

本项目参考了同一维护者/同一环境下已经跑通的三个社区插件，只借模式，不复制业务：

| 项目 | 已落地的事实 | 本项目借用 | 明确不照搬 |
|---|---|---|---|
| [`dsh-swarm`](https://github.com/AiLunSin/dsh-swarm) | 事件溯源、预算账本、Host+Client、本地 HTTP、评审/门禁、bench 与 npm 发布 | “预算要能止损”“事件是唯一事实”“先有 bench 再宣称收益”；Host/Client 分包与发布清单 | 多 agent 调度、worktree、评审市场；本项目只治理一个会话循环 |
| [`dsh-cloud-memory`](https://github.com/AiLunSin/dsh-cloud-memory) | 零运行时依赖的 Host 插件、同源 `/api` + Web 面板、locale、统计页 | Host+Client 双半结构、本地 API、面板交互、i18n、零依赖 | 记忆存储、embedding、检索；本项目不保存内容 |
| [`fish-keeper-console`](https://github.com/AiLunSin/fish-keeper-console) | 需求单/技术方案双文档、只读优先、能力协商、生命周期清理、验收矩阵 | 文档结构与“必须/应当/可以”约束力；只读优先；Windows 权限不伪造；可回滚/可诊断 | 鱼数据适配器、检查点、迁移包；本项目不读写用户业务数据 |

### 1.4 设计判断

“压榨 DSH”最容易走错的两条路：

1. **加更多提示词**：告诉模型“你要高效”，结果每轮都多付一段系统提示，且不可验证。
2. **加更多工具**：让模型自己查预算、自己报告，工具 schema 和调用本身又变成成本。

因此本项目的核心判断是：

> **效率来自减少可回收的浪费，而不是增加更多指令。** 插件应在不进入模型上下文的情况下完成大部分工作；只在“已经值得打断”的时刻，才付一条短消息的成本。

## 2. 用户与场景

### 2.1 目标用户

| 角色 | 画像 | 最在意 |
|---|---|---|
| 重度 DSH 开发者 | 每天用 DSH 改代码、跑测试、查资料，会话长、工具多 | “这轮为什么这么贵？哪里在打转？” |
| 长任务操作者 | 让 agent 自主跑几十分钟，偶尔回来看 | “它有没有停不下来？预算还够吗？” |
| 插件作者/维护者 | 想证明自己的编排/提示词/工具设计更省 | “有没有可复现的对照数据？” |
| 成本敏感用户 | 用 API key 计费，或上下文窗口小 | “别在无关的读取上烧钱。” |

### 2.2 非目标用户

- 只做一次性问答、从不跑长任务的用户。
- 希望插件自动替自己换模型、改提示、删上下文的用户。
- 需要企业级账单、团队成本分摊、合规审计的团队（v1 不做）。
- 需要负载/并发压测的测试工程师（本项目不是压测工具）。

### 2.3 核心任务（JTBD）

| 编号 | 任务 | 用户原话示例 |
|---|---|---|
| J-01 | 轮末复盘 | “这一轮到底花了多少？缓存有没有帮上忙？” |
| J-02 | 定位浪费 | “为什么同一个文件读了三次？为什么工具一直失败？” |
| J-03 | 及时收住 | “预算快到了，别再开新工具了，先把结论给我。” |
| J-04 | 上下文决策 | “现在该压缩，还是该换个更窄的任务？” |
| J-05 | 证明收益 | “开和不开，差多少？别只给我看一个总分。” |
| J-06 | 安全分享 | “我想把回执发给同事，但不想带任何对话内容。” |

### 2.4 关键场景

**S1 长功能开发（主场景）**

用户让 agent 改一个跨 3 个文件的功能。agent 读了 20 个文件、跑了 5 次测试、失败重试 3 次。轮末回执显示：输出 token 正常，但工具失败 3 次、上下文压力 82%、发生 1 次压缩。建议：“下次先跑最小测试，再读实现；上下文已接近阈值，可在下一轮前 `/compact`。”

**S2 打转/重试风暴**

agent 对同一工具连续失败，或对近似参数反复读取。观察模式下只记录并在回执中标记；教练模式在失败连续 2 次后追加一条短提醒；强制模式在工具调用预算耗尽后拒绝新的工具调用，让模型用已有信息收尾。

**S3 上下文将满**

压力表显示 context pressure ≥ 80%。插件不自动压缩，只标记“上下文压力”并给出两个动作：`/compact` 或缩小任务。是否压缩仍由用户/官方压缩策略决定。

**S4 批量任务**

用户连续跑多个小任务，想看哪类任务最贵。面板按会话列出回执，支持导出 CSV；v1 不做跨用户/团队聚合。

**S5 证明插件有效**

维护者用预注册的 9 个任务，对基线/观察/教练/强制四组做对照，发布原始回执与统计，而不是只发一张“节省 37%”的海报。

### 2.5 反场景

- 单轮 10 秒的简单问答：开插件只会增加一次回执写入，收益接近零。
- 必须保留完整长上下文的任务（如整库审计）：压缩和预算都可能伤害质量，应使用观察模式。
- 用户希望“完全自动、永不打扰”：强制模式不适合；观察模式 + 面板更合适。
- 需要精确账单：请用 provider 账单或成本看板；本项目的 token 读数是运行视角，不是账单。

## 3. 范围

### 3.1 v1.0 范围

- Host 侧：会话投影、轮末回执、预算状态机、工具守卫、提醒注入、命令、只读 HTTP API。
- Client 侧：侧边栏入口 + 主面板（会话列表、压力卡、轮次表、回执详情、设置/关于）。
- 中英文文案；浅色/深色主题 token；键盘可操作。
- 本地回执存储、保留策略、导出（Markdown/JSON/CSV）。
- 安装、README、演示数据、基准脚本、CI、MIT 许可证、安全说明。

### 3.2 优先级

| 优先级 | 含义 | 交付要求 |
|---|---|---|
| P0 | 首发必须 | 缺失即不满足 v1.0 |
| P1 | 首个稳定版 | 可以晚一个 minor，但必须在路线图中 |
| P2 | 后续候选 | 不在本单承诺 |

### 3.3 明确不做（非目标）

- 不注册模型工具；不新增工具 schema。
- 不调用 LLM；不做摘要、不选模型、不改系统提示。
- 不读取/保存 prompt 正文、工具参数原文、工具结果原文。
- 不替代 `compaction-basic`、`repeat-tool-reminder`、`spill-policy`、`sessionStats`。
- 不做账户余额、价格表、账单对账。
- 不做跨机器同步、团队协作、权限分级。
- 不做压力测试/并发基准（那是另一个产品）。

## 4. 功能需求

编号规则：`FR-<域>-<序号>`，验收 `AC-<域>-<序号>`。域：`G` 仪表、`D` 诊断、`V` 阀门、`R` 回执/面板、`C` 命令/配置、`X` 横切。

### 4.1 Gauge · 压力读数

**用户故事**

> 作为长任务操作者，我想在会话进行时看到“这一轮花了多少、上下文多满、工具是否在失败”，而不是等结束后翻统计。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-G-01 | 按会话提供：累计输入/输出/缓存读/缓存写 token、当前上下文压力、turns/steps、模型时间、工具时间、工具调用数/失败数、压缩次数。 | P0 |
| FR-G-02 | 按轮提供：该轮 token 增量、工具调用/失败、重复调用计数、墙钟时间、压缩次数、压力峰值。 | P0 |
| FR-G-03 | token 读数优先来自官方投影（`tokenUsage` / `tokenMeter`），不得用字符数估算冒充账单。 | P0 |
| FR-G-04 | 缓存命中率必须给出公式与分母；不得只给一个无定义的百分比。 | P0 |
| FR-G-05 | 数据缺失（服务未挂载、投影未就绪、旧会话）显示“未知/不可用”，不得显示 0 或猜测值。 | P0 |
| FR-G-06 | 每个读数必须能追溯到来源与时间点（例如 `asOfSeq` / `updatedAt`）。 | P1 |
| FR-G-07 | 非活动会话不轮询；面板不可见时暂停刷新。 | P0 |

**验收标准**

| 编号 | 场景 | 通过条件 |
|---|---|---|

## 5. 数据与接口契约（需求层）

### 5.1 回执

```json
{
  "schemaVersion": 1,
  "sessionId": "sess_...",
  "turn": 12,
  "startedAt": "2026-11-13T12:00:00.000Z",
  "endedAt": "2026-11-13T12:04:31.000Z",
  "updatedAt": "2026-11-13T12:04:31.100Z",
  "wallMs": 271000,
  "tokens": {
    "input": 48210,
    "output": 6120,
    "cacheRead": 30100,
    "cacheWrite": 4200,
    "total": 88630,
    "cacheHitRate": 0.365
  },
  "context": {
    "endPressure": 0.78,
    "observedPeak": 0.82,
    "observedFrom": "live",
    "window": 128000,
    "compactions": 1
  },
  "tools": {
    "calls": 14,
    "failures": 3,
    "repeats": 2,
    "maxResultTokens": 9800
  },
  "flags": [
    {
      "code": "failure_streak",
      "severity": "warn",
      "count": 3,
      "turn": 12,
      "adviceKey": "flags.failureStreak.advice"
    }
  ],
  "adviceKey": "advice.runSmallestTest",
  "source": {
    "plugin": "dsh-pressure",
    "version": "0.1.0",
    "asOfSeq": 1234
  }
}
```

**约束**

- 不含 `prompt`、`content`、`arguments`、`result`、`toolOutput` 等正文字段。
- `tokens.input` 是 **uncached input**；`total = input + output + cacheRead + cacheWrite`，表示 token 体积，不是价格。任何一项缺失时 `total` 为 `null`，不把缺失当 0。
- 缓存命中率公式：`cacheRead / (cacheRead + input + cacheWrite)`；分母为 0 或字段缺失时显示“未知”。
- 回执是派生数据，可删除；计数类字段可由会话日志重放，采样类字段（如上下文峰值）不承诺在插件未运行期间重建。会话日志仍是唯一事实源。

### 5.2 信号

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 稳定标识，如 `failure_streak` |
| `severity` | `info / warn / high` | 只用于排序，不换算成分数 |
| `count` | number | 证据计数 |
| `turn` | number | 发生轮次 |
| `step` | number? | 可选步骤 |
| `adviceKey` | string | 固定建议键，由 UI 本地化 |
| `evidence` | object | 计数/阈值/布尔，不含正文 |

### 5.3 预算配置

```yaml
- id: dsh-pressure
  config:
    mode: observe            # observe | coach | enforce
    budget:
      sessionTokens: 0       # 0 = 不限制
      turnTokens: 0
      turnToolCalls: 0
    thresholds:
      contextPressure: 0.8
      budgetPressure: 0.8
      failureStreak: 2
      bloatedResultTokens: 8000
      compactionChurn: 2
    coach:
      maxPerTurn: 3
    storage:
      retentionDays: 30
      maxReceiptsPerSession: 2000
      maxTotalBytes: 52428800
```

### 5.4 时间与 ID

- 时间统一 UTC ISO 8601；UI 按本地时区显示。
- 回执 ID 建议 `sha256(sessionId + "\0" + turn)` 前 16 字节，保证幂等。
- 信号 code 一旦发布不得改名；新增用新 code。

## 9. 风险与开放问题

### 9.1 风险

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-01 | DSH API 处于 pre-stable，投影/事件字段变化 | 升级即坏 | 锁 `engines.dsh`；只依赖公开服务；CI 覆盖当前+前一 minor；抽象适配层 |
| R-02 | token 用量在响应后才可知，强制模式无法保证零超支 | 用户误以为“硬上限” | 文档与 UI 明确“工具刹车，不是 token 硬截止”；回执显示超支 |
| R-03 | 信号误报，打扰用户 | 用户关闭插件 | 默认观察；coach 每轮限 3 条；可静音；阈值可配 |
| R-04 | 与官方/社区插件功能重叠 | 用户困惑、维护负担 | 明确“不重复造”；优先复用；README 写差异；必要时删功能 |
| R-05 | 插件自身增加开销 | 省 token 变花 token | 不注册工具；host-only 投影；提醒仅在触发时追加 |
| R-06 | 回执存储含敏感信息 | 隐私泄露 | 只存数字/信号；参数只存哈希；导出前扫描；权限 0600 |
| R-07 | 上下文压力口径与官方不一致 | 建议错误 | 使用官方 `contextPressure` / `tokenMeter`；文档写口径；不自己估算 |
| R-08 | 基准样本小、结论过度外推 | 信任受损 | 预注册任务；报告样本量与区间；不宣称普遍收益 |
| R-09 | 包名/商标冲突 | 发布受阻 | 发布前检索 npm/GitHub；准备 fallback 名 |
| R-10 | Windows 无 POSIX 权限位 | 安全提示误报 | 显示“权限模型不适用”，不伪造 0600 结论 |

## 10. 需求裁决记录

| 编号 | 问题 | 决定 | 理由 |
|---|---|---|---|
| D-01 | 默认是否强制？ | 默认 `observe` | 没有在用户真实流量上验证过的监督器，不应先动手 |
| D-02 | 是否做“效率分”？ | v1 不做 | 多维度压成一个数字不可解释，容易营销化 |
| D-03 | token 用量自己算还是用官方？ | 用官方 `tokenUsage`/`tokenMeter`；自建只做工具/信号 | 避免重实现 retry/缓存语义，减少误差 |
| D-04 | 强制模式如何止损？ | 预算耗尽后拒绝新工具调用，允许最终回答 | 比直接杀 turn 温和；可测试、可解释 |
| D-05 | 是否保存正文？ | 不保存 | 回执是派生数据，不应制造第二份敏感数据 |
| D-06 | 面板能否改配置？ | v1 只读；变更走命令/配置文件 | 减少写面和权限风险 |
| D-07 | 是否自动压缩/换模型？ | 不做 | 改变模型行为，超出“效率治理”边界，风险高 |
| D-08 | 与 `repeat-tool-reminder` 的关系？ | 不重复提醒，只统计 | 避免双重打扰，尊重已有能力 |
